# 重要复盘：发射功率争议与反复改算法、追求排名的教训

记录日期：2026-10-24。由用户明确要求保存，并写入长期记忆。

**供后续所有参与 Paper3 的 agent 优先阅读。本文是研究与协作复盘，不是新算法规格，不授权恢复 QoS、修改功率范围或重新运行实验。**

## 一、先把责任和结论说清楚

这几天陷入反复改代码、调参数，主要不是因为缺少一个更强的算法名称，而是没有持续守住同一个研究问题：通信时间结构、服务对象、能效分母、公平对象和验收指标先后变化，却常被当作同一算法的性能改进来比较。

用户逐渐把“主算法应当在所有关心的指标上优于对比和消融”当作继续修改的依据；助手没有及时把这个期待转成可验证、允许失败的研究假设，反而多次跟着排名找解释、加机制、换口径。两者形成循环：

> 先期待主算法领先 → 看到某指标不领先 → 优先怀疑实现或参数 → 增加修补 → 目标或模型随之变化 → 新结果与旧结果不再回答同一个问题 → 又根据排名继续修改。

**责任并不对半。用户负责表达业务意图和研究取舍；助手更有责任把意图准确翻译成模型、在实施前指出冲突，并验证代码到底实现了什么。** 不能要求用户先熟悉每个求解器和统计口径，才配得到正确实现。

用户多次质疑“为什么最低车更差”“为什么 QoS 为零”“为什么又出现块内轮换”“为什么不是 SCA”，这些质疑是必要纠错，不应被归为用户的错误。

## 二、证据边界

- 当前对话包含用户转述的多个 agent 报告；转述可证明当时提出过哪些说法，不能自动证明每份旧源码都已逐行核实。
- 本次合并阅读了 2026-10-14 的功率讨论记忆、2026-10-23 的 RF 低功率记录、2026-10-24 的 ABC 验证报告及下一轮诊断文档。
- 前一轮已直接核对 v2 的 4800 行结果、当前候选生成与比较代码，并阅读 Paper5 PDF。本文明确区分这些直接证据与历史转述。
- 不把 agent3 或其他 agent 自报的每个代码缺陷都说成由当前助手亲手编写。这里追究助手侧共同的实现、复核和结论责任；没有证据的具体作者归属不补写。

## 三、用户这一侧需要调整的地方

### 1. 把论文希望成立的贡献，当成了每个实验必须达到的排名

希望主算法表现好是正常的；问题出在“主算法若输给 no-fair/RF-only，就必须继续改到赢”。对话中出现过“消融只要比它差”“不要做出比主算法更好的消融”等表达，这会给开发者错误的验收信号。

消融关闭一个模块后，某项指标变好并不反常：去掉公平或风险控制可能提高网络 EE；去掉 VLC 可能在某些几何和能耗假设下更省能。真正应验证的是模块声称解决的问题是否改善，以及代价是什么。

**改进：要求模块贡献可解释、对比公平、结果可复现；不要求所有指标、所有状态都排名第一。** 如果目标确实是多项同时改善，必须允许实验结果否定该假设，而不是默认改代码就能实现。

### 2. 把不同类型的“不满意”都归为“代码没改好”

这段经历里确有真实代码错误；但也存在模型目标允许的结果。例如取消最低速率约束、只计发射能耗后，RF 可能偏好低功率高 bit/J；最大化最低 EE 也不等于保证最低速率。

**改进：看到不满意的结果，先要求分类：实现错误、求解不足、目标不符合业务、预测误差，还是正常权衡。** 不能只凭排名判断属于哪一类。

### 3. 在尚未固定问题时，同时改变多个条件

时间尺度、QoS口径、车辆数、轨迹、功率准备、目标函数和求解器的讨论交错推进，导致难以知道哪项改变带来哪项效果。提出重新生成轨迹并非错误；若目的是检查真实密度和道路合理性，就有科学依据。若只因为当前轨迹下主算法排名差而换轨迹，就会把测试集变成调参集。

**改进：一次诊断只改变一个主要因素；更改研究场景必须有业务或物理依据，独立于算法排名。** 旧错误场景可以废弃，但应记录理由，不保留对主算法有利的部分作为证据。

### 4. 同时提出了未被形式化兼容的要求

例如既取消全部最低速率约束，又希望低速链路不能被当成优质解；既希望最弱链路明显改善，又希望总体 EE 几乎不付代价。这些诉求值得研究，但不自动由“增加 Jain”“使用 Dinkelbach”实现。

**改进：明确优先级和可接受的代价。** 本阶段已经选择“有限网络 EE 损失下改善最低通信对 EE”，并取消 QoS 优化约束；因此现在不能又将“每对必须达到某速率”当成代码已经承诺的保证。是否改变这一取舍，应显式决策，不能在实现中偷偷补回。

### 5. 将简短的成功汇报过早当成“已完成验证”

“测试全过”“5 s 看起来很好”“这是真实公平价格”“可以定稿”容易让人相信关键问题已解决。但单元测试、机制小样本、长轨迹评价和独立测试回答的是不同问题。

用户没有义务逐项检查代码。更有效的追问是：**同什么比、保持了什么不变、数据来自哪个版本、这项证据还不能证明什么？** 助手应主动提供这些信息，不应等用户追问。

## 四、助手这一侧犯的关键错误

### 1. 把自己的实现习惯当成用户要求，且没有提前解释后果

早期“每 10 ms 重新配对，按 100 ms 累计服务”天然允许错峰与集中传输。时间调度本身并不是通信理论错误；错误在于没有明确告知这种自由度，并把它用于用户希望研究的固定通信对持续资源分配。

后来又混用了 plan10、plan100 和 hold100 的结果。100 ms 提前规划十个子时隙，与100 ms保持同一组配置，不是同一个协议。由一种方案的结果推断另一种方案优劣，是具体判断错误。

**应做而没有及时做：在写优化器前，用六辆车、两个块的例子确认每条链路什么时候发、是否可停、谁受服务、何时考核。**

### 2. 服务记账与 EE 口径没有一次讲清、改全

发送侧记账本身可用于有向业务；但不能在用户已经选择通信对参与模型后，还按“每辆车都要发送”判定全部达标。反过来，一条 A→B 也不能宣称完成了 A、B 两份独立发送业务。

“EE只能按发送车算，这是量纲决定的”也说得过头。EE可以定义在通信对上，关键是同一条有向传输的有效比特和归属能量各计一次。当前研究只计发送能量是明确的范围选择，不是通信对 EE 在数学上不允许。

修改 pair 指标时，只改输出而未同步目标、接收端需求或块级逻辑，会出现代码自洽性缺口。应核查从定义到决策再到记录的完整路径，而不是看到一处改了就宣布完成。

### 3. 未先检查目标函数会鼓励什么行为

在只计发射功耗、没有最低速率时，低功率偏好可以直接从 RF 模型推导。没有先做这个检查，却把出现低功率、低速率、高 EE 解释为算法奇怪，导致不断围绕症状修补。

同样，Jain 提高不等于最弱链路提高；短窗口公平不等于全程车辆公平；最大化最小 EE 不是最大化最小速率；网络预算不是逐链路服务约束。这些都应在运行前解释。

### 4. 用解释代替验证，过早给出确定归因

历史汇报中有几类不能接受的推断：

- 从两个算法的结果差异直接断定“这是公平的真实价格、不是实现缺陷”。没有更充分求解或同状态对照，不能排除候选遗漏、局部解和路径差异。
- 把有限个运行结果称作 Pareto 前沿。最多说明在已比较结果中未被支配，不证明整个可行域中 Pareto 最优。
- 从若干高功率状态决策一致，推出公平门不存在实现错误。局部一致不能覆盖整个决策路径。
- 把 J=0.716 与 J=0.787 的 EE 比值称为“同等公平水平”。比较对象不等公平，表述错误。
- 将“EE与公平性同时第一在物理上做不到”说成普遍结论。权衡常见，但相对于非最优对手，改进方法可以同时改善多项指标；没有通用不可能性证明。
- 把实际/预测中位数接近 1 当成无偏、把候选总数接近当成截断无影响。
- 把 CRLB 下界、线性高斯模拟参考、实际预测方差和经验区间覆盖混称，甚至提前说“已到理论界”。

**正确做法：先说观察到了什么，再列竞争解释，最后用最便宜的固定状态检查区分。** 没查清时说“尚不能排除”，不把好听的机制故事写成实证结论。

### 5. 实现验证过于表面，测试未总是对应声称的性质

对话记录中的具体错误包括：功率发送/接收轴混淆、增益形状检查无效、SCA接受逻辑原地返回、Stage B将辅助变量当功率、均值信道错误删除方差项。这些属于实际实现问题，不是正常性能权衡。

语法通过不能证明公式正确；“不退步”不能识别算法从未移动；等功率样例可能掩盖轴错误；与同一份错误实现互相对照也不是独立验证。

还曾把直接非凸 SLSQP 作为 SCA 的替代而没有提前明确说明。另一方面，SCA构造出的合适子问题用SLSQP数值求解，并不等于“没用SCA”。问题在于近似模型、变量变换、定义域、梯度及收敛条件是否一致，而不是底层函数叫什么名字。

### 6. 顺着“让主算法赢”的要求修改对照和解释

助手应拒绝人为削弱消融、选择性保留有利结果和更换评价口径。历史上主方法无公平门、旧消融带公平门，却仍被用作单因素对比，就是不干净的消融设计。

同一候选预算、物理模型、合法动作和求解精度应尽量对齐。恢复旧基线可以为了可复现或忠实适配，不能因为它比较弱。文献适配和纯消融也不能混为一类。

还把不同场景的正负收益平均成“公平几乎免费”，掩盖个别场景明确的 EE/QoS 损失。应逐场景报告代价，再说明汇总方式。

### 7. 版本与研究说明没有同步，长跑启动得太早

多个版本、交接包和入口说明并存，导致改了规格但旧代码仍运行、运行了新代码却引用旧指标。此次复盘时，项目顶层入口仍写着已过时的“no-fair核心暂称DJ”。

这是实际的协作缺陷。运行路径、源码快照、基础层与场景标识、模型口径、输出字段应该绑定。无需每次打一个巨大包，但必须能回答“这张表到底由哪套问题和代码生成”。

在通信规则或单位尚未核清时反复启动长跑，增加等待和沉没成本，也让双方更想为已有结果寻找解释。应该先用很小的、能人工复算的例子排除基础问题。

## 五、与此前发射功率争议合并复盘

### 1. 当时助手的错误：把可限定的研究范围扩大成必须解决的器件问题

2026-10-14的记忆记录了用户的反馈：长时间纠缠 RF/VLC 功率、量纲和公式，使用户一度认为找不到可用模型，后来才说明可以限定为通信发射能效。

这个反馈应保留。可以明确只研究通信发射能量，不必为了资源分配论文自动增加照明、LED驱动、接收电路、处理器或整车能耗。助手应先提出范围内可用的模型与必要条件，不应把每个简化都扩大为新课题。

但限定范围也不替代物理核对：RF辐射功率、VLC光功率/调制参数、光电转换后的电流平方、信号/干扰/噪声单位必须一致。不能仅因公式出现光功率平方就认定量纲错，也不能只改变量名称就认为公式全对。

### 2. 低 SINR 不等于功率小，增加全网功率不等于改善通信

固定配对、线性同频干扰下，同时放大全部 RF 功率：

\[
\mathrm{SINR}_i(\alpha)=\frac{\alpha S_i}{\alpha I_i+N_i}.
\]

干扰占主导时，它趋于 S_i/I_i；共同抬高功率可能主要增加能耗。只提高某一条链路功率则是不同操作：该链路可能受益，同时给其他链路增加干扰。

旧记忆提及40 m固定配对的加功率诊断。本次没有重新定位并复算其原始数组，因此不把那个数值当作当前场景事实；保留的是诊断方法，而不是旧场景的普遍结论。

### 3. RF 低功率高 EE 有限，不是“无限能效”

固定其他链路和信道、A>0，且只计发射能耗：

\[
R(p)=B\log_2(1+Ap),\qquad \eta(p)=R(p)/p.
\]

\[
\eta'(p)=\frac{B}{\ln2}\frac{Ap/(1+Ap)-\ln(1+Ap)}{p^2}<0\quad(p>0).
\]

\[
\lim_{p\to0^+}\eta(p)=BA/\ln2,\qquad \lim_{p\to0^+}R(p)=0.
\]

这意味着该固定条件下的RF单链路偏好最小允许功率，EE极限有限而速率趋零。当前1 mW下限也不允许功率无限缩小。不能由这个单链路推导断言所有异构全网联合最优解的每个功率都必在下限。

VLC在当前归一化模型下信号项含p²，且噪声可含p项，所以其低功率EE行为不同。差别主要在SINR对功率的依赖，不在是否用了对数。等效SINR统一速率比较，不会自动排除低速高EE，也不保证VLC应当获胜。

### 4. 不应再采用的“修复”方式

- 为压低 RF-only 的 EE 而随意抬高 RF 最小功率。
- 为让 VLC 更占优而人为规定 VLC 配额或选择有利轨迹。
- 为制造功率内点最优而无业务依据地加入电路开销。
- 取消 QoS 后仍保留隐含的最低速率过滤，并声称“没有QoS约束”。
- 将通信发射能效直接解释成整机节电比例。

若业务必须保证最低速率，就明确定义服务要求并公平施加于全部方法；若保持q=0，就诚实接受它可能选择低速高EE动作。这是需要明确的研究取舍，不是继续调参可以自动兼得的事情。本复盘不替用户重新选择。

## 六、哪些事情并不是错误

- 发现新问题后重新定义研究对象，不等于前期全部白做。旧结果可以作为探索记录，但不能与新问题混作最终比较。
- 时分调度本身是合法模型；它不符合本项目后来明确冻结的固定块需求，才应在本项目中排除。
- 主算法在某一指标上输给消融，并不自动说明算法错误。
- 使用Jain、Max-Min、SCA、Dinkelbach或MASAC都不是原罪；错误是声称这些名字自动保证业务含义、全局最优或结果排名。
- 小样本探针、负面结果和发现候选不足都有价值；错误是把它们过早包装成普遍结论。
- 用户要求停止无意义的长跑、检查底层通信过程，是正确纠偏。

## 七、以后怎样避免重演：最小工作规则

### 1. 先写清问题，后谈算法

每次实际改变模型时，只需明确六项：谁通信；块内能否改配置/停发；QoS约束还是仅评价；比特与能量归属；公平对象与时间范围；决策可见的信息。规则变化要记录影响哪些旧结果。

截至本次复盘：100 ms完整配置保持；无块内轮换、提前停止和跨块补偿；通信对吞吐只计一次；优化最低块级通信对EE并限制网络EE损失；QoS仅事后评价；通信发射能耗范围不自动扩大。这些是当前状态，不是不可修改的物理定律。

### 2. 每次异常先分类，不先找一个新模块

| 类别 | 最小检查 | 合理动作 |
|---|---|---|
| 代码/记账错误 | 两块人工算例、非等功率、零/极端信道、独立数组复算 | 修具体缺陷，重跑受影响结果 |
| 求解不足 | 同状态、同候选、增加迭代/起点，再检查候选截断 | 修改搜索或求解预算 |
| 模型目标允许不想要的行为 | 边界推导、固定状态反例 | 显式讨论业务目标，不能偷偷加门槛 |
| 预测误差 | 同动作的预测/真实结果及独立样本覆盖 | 校准误差模型或评估风险控制 |
| 正常多目标权衡 | 同状态同参考的成对比较 | 报告收益和代价，不强迫全面领先 |

### 3. 固定证据链，不固定理想排名

先有人工算例，再有少量预选状态的配对检查，最后才做长轨迹/多种子。每一级有具体要检验的性质；不要为了增加“测试通过数”写重复测试，也不要在模型尚未确定时一次跑完所有组合。

开发集允许调试；用于调参、挑阈值的结果不能再冒充未见测试。结果不如预期时保留结果和版本，优先缩小结论，不以主算法胜负决定删留。

### 4. 正确设计消融

消融只移除对应模块，尽量保留其他搜索预算、约束、信息与物理设置。允许出现“去掉模块后EE更高，但弱链路或风险更差”。若所声称收益也没有出现，应考虑模块无效、冗余或当前场景不需要，而不是削弱对手。

### 5. 助手必须改变的汇报方式

- 先回答用户真正的问题，明确已确认、合理推测、未验证。
- 不再无依据地说“真实价格”“物理不可能”“已经达到下界”“不是bug”“已定稿”。
- 不用换口径维护旧结论；发现错误，说明错在哪里、影响哪些结果、最小修正是什么。
- 给出可执行的下一步，并尽量用已有日志或固定状态验证，减少重复长跑。
- 不以用户希望的排名代替独立判断，也不把正常研究假设夸成方向不可行。

## 八、最值得长期记住的一句话

**研究要验证“这个机制在什么条件下解决了什么问题、付出多少代价”，而不是不断修改实验，直到主算法在表格里全部排第一。助手应帮助固定问题和证据，而不是帮助维护预设结论。**

### 10.1 我的错误（按对结论的危害排序）

1. **协议没有先钉死就写优化器。** 我把"10 ms 重新配对、100 ms 累计服务"当成默认，还混用过 plan10、plan100、hold100 三种结果。时间调度本身是合法模型，错误在于没有先说明这种自由度、也没有确认它是否符合本项目的固定块需求。
2. **没有先推导目标会鼓励什么行为。** 固定其他链路、只计发射能耗时，RF 单链路 `η(p)=R(p)/p` 单调下降，`η→BA/ln2` 而 `R→0`。所以"RF 偏好最低功率"是模型性质，不是算法异常。我是先看到低功率、低速率结果，再围绕症状修，顺序反了。
3. **用解释代替验证。** 说过"真实公平价格""Pareto 前沿""物理上不可能""已到理论界""不是 bug"这类话。它们需要同状态对照、全域搜索或覆盖率证据，当时都没有。
4. **把测试和审计通过当成性质成立。** 单测全绿说明接口没被破坏，独立审计通过说明输出自洽；两者都不说明策略学到了东西，也不说明物理口径正确。汇报时它们却总在最显眼的位置。
5. **顺着排名修补对照与口径。** 主方法无公平门、旧消融带公平门，仍被当成单因素比较，这是不干净的消融设计。
6. **规格、代码、结果、文档没有绑定。** 改了规格旧代码还在跑，跑了新代码还引用旧指标；项目入口长期写着旧 DJ 主方法。
7. **本轮（10-24）复发的两条同类错误，都已发现并修正：**
   - 写 50/100 车验收文档时先凭记忆填数、后读 JSON：50 车块 4 与块 5 的参考网络 EE 分别是 1.875e10 与 2.029e10，最低 EE 分别是 8.71e8 与 1.046e9，第一版表格把两组混在一起。**先结论、后核对。**
   - `credit.py` 第一版把合法性预筛放在计数之前，导致 `generated` 只统计通过预筛的候选、`skipped_illegal` 恒为 0（n=100 只报 396，实际尝试 1425）。**自报统计不诚实。** 已改为全量计数并加测试，最终 n=50 为 400/221/154/25、n=100 为 1425/396/979/50（尝试/合法/拒绝/空操作）。

### 10.2 对前文两处表述的补充
